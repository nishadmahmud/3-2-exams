**1. (a) Describe the role of lexical analyzer. Why is analysis portion of compiler normally separated into lexical analysis and syntax analysis?** [1+1]
> **Answer:**
> **Role of Lexical Analyzer:** It reads the source program as a stream of characters, groups them into meaningful sequences called lexemes, and produces a stream of tokens for the parser. It also strips out whitespace and comments.
> 
> **Why separate Lexical and Syntax Analysis?**
> 1. **Simplicity:** Separating the tasks simplifies the design of both phases. The parser doesn't need to deal with whitespace or character-level complexities.
> 2. **Efficiency:** A specialized, separate scanner can process characters much faster.
> 3. **Portability:** Input-device-specific peculiarities can be restricted entirely to the lexical analyzer.

**3. (a) What is the role of the parser?** [2]
> **Answer:**
> **Role of the Parser (Syntax Analyzer):**
> 1. It obtains a string of tokens from the lexical analyzer and verifies that the string can be generated by the grammar for the source language.
> 2. It constructs a syntax tree (or parse tree) for the token stream and passes it to the semantic analyzer.
> 3. It reports syntax errors (like missing tokens or mismatched braces) accurately and provides error recovery strategies so compilation can proceed.

**6. (a) Draw the model of LR parser. Write the LR parser algorithm.** [1+2]
> **Answer:**
> **Model of LR Parser:**
> The LR parser consists of an input buffer, a stack (containing states and grammar symbols), a parsing table (action and goto parts), and a parsing program.
> 
> ```mermaid
> graph TD
>   input["Input Buffer ($a_1, a_2 ... a_n\$)"]
>   stack["Stack ($s_0 X_1 s_1 ... X_m s_m$)"]
>   program["Parsing Program"]
>   table["Parsing Table"]
>   action["Action Table"]
>   goto["Goto Table"]
>   table --> action
>   table --> goto
>   program --> input
>   program --> stack
>   program --> table
>   program --> Output["Output"]
> ```
> 
> **LR Parser Algorithm:**
> 1. Initialize the stack with the start state $s_0$. Let $a$ be the first input symbol.
> 2. Let $s$ be the state on top of the stack.
> 3. Consult the action table entry `action[s, a]`:
>    *   If `action[s, a] = shift s'`, push the input symbol $a$ and state $s'$ onto the stack. Advance the input to the next symbol $a$.
>    *   If `action[s, a] = reduce A -> β`, pop $2*|\beta|$ elements off the stack. Let state $t$ now be on top. Push $A$, then push state $s' = goto[t, A]$. Output the production $A \rightarrow \beta$.
>    *   If `action[s, a] = accept`, parsing is successful. Terminate.
>    *   If `action[s, a] = error`, call the error recovery routine.
> 4. Repeat step 2 until accept or error.

**(b) (i) Show that the following grammar** [1+1]<br>
$S \rightarrow AaAb \mid BbBa$<br>
$A \rightarrow \epsilon$<br>
$B \rightarrow \epsilon$<br>
Is LL(1) but not SLR(1).<br>
(ii) Show that every LL(1) grammar is an LR(1) grammar
> **Answer:**
> **i) LL(1) but not SLR(1):**
> *   **LL(1) Check:** For $S$, the productions are $AaAb$ and $BbBa$. $FIRST(AaAb) = \{a\}$ and $FIRST(BbBa) = \{b\}$. Since their FIRST sets are disjoint ($\{a\} \cap \{b\} = \emptyset$), the grammar is LL(1).
> *   **SLR(1) Check:** Let's calculate the FOLLOW sets for $A$ and $B$.
>     $FOLLOW(A) = \{a, b\}$ (from $S \rightarrow AaAb$ and the fact that $A \rightarrow \epsilon$)
>     $FOLLOW(B) = \{a, b\}$ (from $S \rightarrow BbBa$ and the fact that $B \rightarrow \epsilon$)
>     In the initial state $I_0$ of the LR(0) automaton, we have the items:
>     $S \rightarrow \cdot AaAb$
>     $S \rightarrow \cdot BbBa$
>     $A \rightarrow \cdot$
>     $B \rightarrow \cdot$
>     Because $A \rightarrow \cdot$ and $B \rightarrow \cdot$ are completed items, SLR parsing requires us to reduce by $A \rightarrow \epsilon$ on symbols in $FOLLOW(A)$ and reduce by $B \rightarrow \epsilon$ on symbols in $FOLLOW(B)$. Since both follow sets contain $a$ and $b$, on seeing either input, we have a **Reduce-Reduce conflict**. Thus, it is not SLR(1).
> 
> **ii) Every LL(1) grammar is LR(1):**
> An LL(1) grammar can be parsed deterministically from left to right with 1 lookahead symbol, making decisions top-down. LR(1) is the most powerful class of deterministic bottom-up parsers, and its state machine incorporates 1 symbol of lookahead into the items themselves. Because LR(1) parsers delay decision-making until the entire right-hand side of a production is seen (unlike LL(1) which must decide at the beginning), it has strictly more information. Any grammar that can be parsed deterministically top-down (LL(1)) can also be parsed deterministically bottom-up (LR(1)).

**(c) Suppose parameters are passed by value instead of by reference. Can two names be aliases of one another? What if copy-restore linkage is used?** [2]
> **Answer:**
> **Pass by Value:** In pass-by-value, the formal parameter receives a copy of the actual parameter's value. Since the formal parameter is given its own distinct memory location, it cannot become an alias for the actual parameter or any other name. Two names cannot be aliases of one another under pure pass-by-value.
> 
> **Copy-Restore (Value-Result):** Data is copied into the local variable on call and copied back to the caller's variable on return. Within the function's scope, the names still refer to separate local memory locations, so they are not aliases during execution. However, if the same global variable is passed to two different parameters, the final value of the global variable depends unpredictably on the order in which the local copies are restored (copied back) to the global location.

**(b) Write an algorithm to partition a sequence of three-address statements into basic blocks.** [2]
> **Answer:**
> **Algorithm to Partition 3AC into Basic Blocks:**
> 1.  **Identify Leaders:** The first statement in a basic block is called a leader. Leaders are determined by the following rules:
>     *   The very first statement of the three-address code sequence is a leader.
>     *   Any statement that is the target of a conditional or unconditional `goto` is a leader.
>     *   Any statement that immediately follows a conditional or unconditional `goto` is a leader.
> 2.  **Form Blocks:** For each leader, its basic block consists of the leader and all statements up to, but not including, the next leader (or the end of the program).

**(c) Write Machine Instruction code for the following 3 address code** [4]<br>

| (i) | (ii) | (iii) |
| :--- | :--- | :--- |
| `x=a[m]`<br>`y=b[n]`<br>`a[m]=y`<br>`b[n]=x` | `y=*q`<br>`q=q+4`<br>`*p=y`<br>`p=p+4` | `i=5`<br>`L1: if i<1 goto L2`<br>`i=i-1`<br>`goto L1`<br>`L2:` |

> **Answer:**
> **(i) `x=a[m]; y=b[n]; a[m]=y; b[n]=x`**
> ```text
> LDF R1, m
> MULF R1, #4       ; Assuming 4 byte words
> LDF R2, a(R1)     ; R2 = a[m]
> STF x, R2         ; x = a[m]
> 
> LDF R3, n
> MULF R3, #4
> LDF R4, b(R3)     ; R4 = b[n]
> STF y, R4         ; y = b[n]
> 
> STF a(R1), R4     ; a[m] = y
> STF b(R3), R2     ; b[n] = x
> ```
> 
> **(ii) `y=*q; q=q+4; *p=y; p=p+4`**
> ```text
> LDF R1, q
> LDF R2, 0(R1)     ; R2 = *q
> STF y, R2         ; y = *q
> ADDF R1, #4       ; q = q + 4
> STF q, R1
> 
> LDF R3, p
> LDF R4, y
> STF 0(R3), R4     ; *p = y
> ADDF R3, #4       ; p = p + 4
> STF p, R3
> ```
> 
> **(iii) `i=5; L1: if i<1 goto L2; i=i-1; goto L1; L2:`**
> ```text
>     MOV R1, #5
>     MOV i, R1
> L1: MOV R2, i
>     CMP R2, #1
>     BLT L2
>     SUB R2, #1
>     MOV i, R2
>     B L1
> L2:
> ```
